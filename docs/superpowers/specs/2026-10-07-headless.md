# Headless terminal flow

User correction: no open browser, no routine setup/start command, one installation then `??` works in every new terminal. This supersedes the earlier Chrome default and browser workflow.

Default backend becomes local Ollama, default model qwen2.5-coder:1.5b. The installer downloads a user-owned Ollama runtime only if no usable binary exists, starts a dedicated loopback server on 127.0.0.1:11435 with cloud features disabled, downloads the selected model, verifies inventory and performs a validated inference smoke check before declaring ready. It requires no root or browser. Routine ask/suggest checks and automatically starts the runtime if needed, without downloading models silently. Saved legacy Nano configuration migrates to the headless default; saved local Ollama model selection is preserved. No browser-launching active CLI paths remain.

Runtime stores models under private XDG Nano Shell state, uses an interprocess lock to serialize starts, retains process identity for owned shutdown, and never kills an arbitrary PID or another existing Ollama service. Start readiness and stop readback must remain honest. No source context or generated responses appear in daemon logs. If runtime or model is missing, the error explains that installation was incomplete; it must not request Chrome initialization.

Installer defaults to one-time runtime/model provisioning. --no-start is an explicit source-only mode for CI/offline preparation and skips provisioning/service enablement. Default service runs the headless runtime rather than Python browser bridge. Installer disables an older owned Nano bridge service before migration; never changes unrelated service ownership. Legacy files may remain for historical tests but no browser dependency is in the normal product flow. Uninstall removes only owned resources, preserves downloaded models by default, and stops verified owned processes.

Keep current vetted argv policy; add read-only Docker inspection (`docker ps`, `docker info`, `docker version`) so the user's `?? is docker up` works without granting daemon-mutating commands. Do not permit `docker run/exec/compose`, formatting templates, or arbitrary Docker globals.

Verification: tests for automatic startup, concurrency/ownership, setup/install failure truthfulness, runtime download extraction, saved-config migration, installer starting/provisioning once, and Docker policy. Actual network and host installation remain blocked by sandbox restrictions and are not described as verified.
